# Changelog

## [Unreleased]

### Added
- **`luuvcrm_passive`** (`settings.KEYS`, site_config): the switch for a site that carries the app without being a restaurant. Branding, the `/app` deep-link redirect and every patch ask `settings.passive()` first and stay out. On the live bench that site is the clothing shop; without this, its login page said "Luuv Fryxo".
- **`deploy/vps-deploy.sh` and `deploy/REMOVE.list`** — the deploy that fits the live host: the app directory is not a volume and not a git checkout, it holds the clothing site's code that this repo does not, and the workers keep their own copies. Preflight, backup, a rehearsal in a throwaway container, the overlay deploy, rollback. `docs/DEPLOY_RUNBOOK.md` §3–§6 now describe that host rather than an SMB share that does not exist.
- **A till takes more than cash and card** (`pos.html`, `setup_doctype.add_payment_mode`): the payment and split dialogs list whatever payment methods the POS Profile carries — PickMe, and whichever aggregator comes after it — alongside the built-in Cash, Card and Split. Everything downstream was already generic: the invoice books whatever mode it is handed, the shift close builds its rows from the profile and auto-fills every non-cash one, the manager's payment mix groups by mode. The profile *adds* buttons and never removes them, because a real profile often lists only `Cash` — that table never had to be filled in while the buttons were written into the page. `add_payment_mode` wires one up end to end, since three things have to line up and each fails somewhere different: the Mode of Payment, an account per company (or the profile will not even save), and the row on the profile.
- **The look is the restaurant's** (`settings.KEYS`, `templates/includes/brand.html`): accent colour, its pressed shade, a logo and the two home-screen icons. Included last in every screen's `<head>`, so one field in the Desk repaints all 24 — while each page keeps its own default and still renders on a site with no settings. The three static PWA manifests are replaced by `luuvcrm.api.manifest`, built from the same settings.
- **`/owner`** — every branch side by side (revenue, sales, average bill, cash, approvals waiting) and the setup behind them: Cost Center, Warehouse, which till belongs to which branch, which manager sees only theirs. Phase 2c built the multi-restaurant machinery and left it reachable only from a Python console; `roles.require_owner()` existed and nothing called it. A branch with no Cost Center reads "not set up" rather than `Rs 0`.
- **The 24 DocTypes ship as JSON** under `luuvcrm/zeloura/doctype/`, `custom: 0`, so `bench migrate` syncs them and a field change finally has a migration path. `setup_doctype` keeps a roll-call for the drift report and checks rather than creates — `install_app` syncs the JSON before `after_install` runs.
- **`required_apps = ["erpnext", "hospitality"]`** in `hooks.py` (B4). Not a pyproject dependency: those are pip packages, these are Frappe apps bench resolves, and `install_app` reads this hook to install them first.
- **The schema, declared in the repo** (`luuvcrm/setup_doctype.py`, ported from the `schema-in-repo` branch): 24 DocTypes, 32 custom fields, 2 property setters, the roles and DocPerms, the branch column and the reference rows the screens need. `after_install` runs it, so `bench install-app luuvcrm` provisions a fresh site instead of needing ~27 `setup_*` endpoints called by hand in an undocumented order. `report_drift()` reports read-only what a site is missing — zero on this one.
- **A branch is a Cost Center, not a Company** (`luuvcrm/branch.py`): one owner, two restaurants, one legal entity and one Chart of Accounts, separated by Cost Center, Warehouse and permissions. `Restaurant.cost_center`, `Restaurant.warehouse` and `POS Profile.restaurant` make the mapping explicit, because a shared company means `POS Profile.company` no longer identifies a branch. `branch.check()` reports the configuration mistakes that look exactly like working — two branches sharing a cost centre, a group cost centre where a leaf is needed, a till attributed to no branch.
- **Branch scoping groundwork** (`luuvcrm/branch.py`, ROADMAP Phase 2c): a `restaurant` Link field on POS Order, Purchase Bill, Expense, Wastage, POS Approval, POS Cash Movement and LF Activity Log, stamped on insert. The patch adds the column only — the backfill of historical rows is `luuvcrm.branch.backfill`, run by hand on a day of its own. `branch.current()` replaces the fourteen `get_value("Restaurant", {}, "name")` lookups — *the first restaurant, whichever it is* — with a real resolution chain, and returns `None` rather than guessing when there is more than one. Nothing anyone can see changes on a one-restaurant site; the visibility half (flipping reads to `get_list`) is deliberately separate.
- **Front-end error log, wired up at last** (`luuvcrm/api/errors.py`): `log_client_error`, `get_client_errors`, `resolve_client_error`, `clear_client_errors`. `lferr.js` had been posting every staff-PWA error to `luuvcrm.api.log_client_error` since it shipped — an endpoint that did not exist — and because the reporter is fire-and-forget inside a try/catch, every report 404'd silently while `/errors` and the `/admin` badge showed nothing. Repeats collapse onto one row by fingerprint (app, kind, message, source, line) with a hit count, so a render loop across eight tills is one entry; reads are manager-gated; a daily job drops fixed rows after 30 days and open ones after 180.
- **Print Receipt** (`pos.html`): "🖨️ Print Receipt" button in order success overlay. Calls `get_receipt_print_data` API and renders a formatted receipt in a new print window.
- **Print KOT** (`waiter.html`): "🖨️ Print KOT" button in order placement success overlay. Calls `get_kot_print_data` API and renders a Kitchen Order Ticket in a new print window.
- **Print KOT** (`kitchen.html`): "🖨️ KOT" button in each order card footer. Re-prints KOT from the kitchen view.
- **Paper width override** (`pos.html`): `localStorage['lf_paper_cols']` sets the printer's column count (58mm roll = 32, 80mm = 48; default 32). Read once into `PAPER_COLS` and used for both the `----` divider and the right-aligned amount padding in `flatten()`, so an 80mm till no longer needs a code change.
- **Print API endpoints** (`api.py`): `get_receipt_print_data(order_name)` and `get_kot_print_data(order_name)` — server-side data endpoints that return structured print data (items, totals, payment mode / table, waiter, notes).

### Removed
- **The app's own `WhatsApp Account` DocType.** It belongs to the `frappe_whatsapp` app (13 fields, module "Frappe Whatsapp"); the 5-field copy this app shipped under the same name would have overwritten the real one on the first migrate. `api/wa.py` reads the installed one and creates nothing — a site without frappe_whatsapp simply sends no messages.
- **`website_route_rules` and the `home_page` hook**, three days after they arrived. Hooks are bench-wide, and this app is installed on a second site that is not a restaurant (its DocTypes live in a module this app owns): the rules turned that site's `/home` into the restaurant's landing page and the hook overrode its front door. `/order` and `/home` are ours by install order — `required_apps` puts erpnext before this app, which is the order the live site has — and `/` comes from Website Settings, set on a fresh site by `setup_doctype.ensure_home_page()`. The page files are `order.html` and `home.html` again.
- **The Zeloura fashion code** — `zeloura_api.py`, `zeloura_setup.py`, the theme and populate scripts, `test_child_parent.py`, and the `/network` and `/shop` pages: 11 files for a different product. Nothing restaurant-side imported any of it and its DocTypes are not on the site.
- **11 one-off scratch scripts** (`check_*`, `debug_*`, `fix_*`) — gitignored, so never in the repo, but sitting in the importable package on the server.
- **The duplicate 70 MB print APK.** One copy, in `public/`.
- **`/app2`** — a second copy of Frappe Desk, added when `www/app.py` (the customer PWA) sat on `/app` and shadowed Desk. That file is long gone, and `/app2` was only ever half-wired: the `website_route_rules` and `on_session_creation` hooks its own docstring says it needs were never added, so `redirect_desk_login` never ran and `/app2/<doctype>` 404'd. Dropped from `KNOWN_APPS` with it.

### Fixed
- **Permission grants failed on the live site's own rows** (`roles._perms_valid`). Found by the deploy rehearsal on a restored copy of the live database: `add_permission` re-validates every row of a doctype, and hospitality's Restaurant, Restaurant Table and Restaurant Menu come with `import: 1` on rows of a DocType that is not importable, plus System Manager twice at level 0. Frappe never validates standard rows until something writes a permission — then it refuses every write. Both permission tables are repaired first (duplicates merged into the OR of their flags, `import` off where it never applied), which is what lets `grant_pos_permissions` and `grant_app_permissions` run at all.
- **The staff invite link raised `AttributeError`** on Frappe 15.101: `staff_invite_link` called `User._reset_password`, a private method this version does not have. The public `reset_password(send_email=False)` returns the same link.
- **The payables list hid the newest bills.** `get_due_bills` took the 200 oldest owed bills; the live site owes more than that (every bill approved before `payment_status` existed reads as owed), so bills entered this week were not on the list that exists to show them. The cap is 2,000.
- **`LF Client Error` had System Manager permissions only.** It is created at runtime, after the grant patch has run, so managers could not read the error log. Creation now grants the rows `roles.APP_DOCPERMS` declares.
- **`remove_payment_mode`** (`setup_doctype`), the mirror of `add_payment_mode`: takes a method off every till's profile and nothing else. The deploy runs it for Bank Draft, which two live profiles list and no cashier has ever seen.
- **Every PWA icon 404'd.** `/icon.svg` and `/manager-icon-{192,512}.png` were referenced by four pages and all three manifests and none of them existed — so "Add to Home screen" produced an app with no icon, and the kitchen and waiter desktop notifications had none either. The real files are under `/assets/luuvcrm/`.
- **`hooks.py` pointed `extend_website_context` at `overrides/branding.py`, and that hook does not exist in this Frappe** — so the module had never been called and every page kept a hard-coded palette. It is a Jinja global now, which works on pages with no `.py` too.
- **`/track` was enumerable by order name** (S7b, the last open Phase 1 finding): names are a guessable sequence, so walking them read back what every table ate and the customer name on each order. A guest now presents an HMAC keyed on the site's encryption key; an unsigned request and a nonexistent order get the same empty answer. It had been deferred on the grounds that it changes links already in customers' hands — no message sends a `/track` link at all.
- **Take-away lines were charged service charge by the POS Order controller** (`zeloura/doctype/pos_order/pos_order.py`): the controller Frappe actually loads computed it on the full subtotal. Totals were right in practice because `api._apply_takeaway_service_charge()` overrides after every save, but anything saving an order outside that endpoint — the Desk, a future path — got it wrong in the restaurant's favour. The correct logic existed only in the duplicate `luuvcrm/doctype/` folder that Frappe never loaded, and would have gone with it.
- **A cashier could approve their own request, and then delete the record of it** (`roles.APP_DOCPERM_REVOKE`): `POS Approval` was created granting Cashier read/write/create/delete, and Frappe exposes every doctype over its generic REST API where DocPerms are the only check — so loading the row, setting `status` to "approved" and saving it skipped `resolve_approval` and `block_self_approval` entirely. Same shape on `Purchase Bill` and `Expense`; and `Cashier: rwcd` on `Tour Guide` / `Guide Cashback Txn` let the till edit what the restaurant owes a guide. Verified reachable before fixing, and there are tests that try it.
- **A Restaurant Manager could not read Purchase Bill, Expense, Wastage or POS Approval** — their own screens — while a Cashier could, and `Restaurant Table` was manager-only. Harmless while every read used `frappe.get_all` (which ignores permissions); a blank screen the moment one did not.
- **`/kitchen` rendered for anyone, logged in or not** (`www/kitchen.py`): the guest branch set `frappe.local.flags.redirect_location` and then fell through without raising `frappe.Redirect`, so the flag was set and ignored and the whole display — every open order, table by table — came back 200 to a stranger. Now raises, and gates on Kitchen roles.
- **`/qrcodes` was public** (`www/qrcodes.py`): it lists every table and the kiosk URL that orders against it, so anyone could order to any table without being in the building. Login + manager now.
- **Role gates added to `/waiter`, `/purchases` and `/qrpromo`** — all three checked for a login and nothing else, so any signed-in user could read what the restaurant pays its vendors or mint promo codes.
- **`lferr.js` added to `/waiter` and `/kitchen`** — the error reporter was on six pages and missing from the two the floor and the kitchen actually hold.
- **Divider printed half-width** (`pos.html`): a `----` line in the Google Docs layout was hardcoded to a 32-character dash string, so it fell short of the paper and printed left-aligned, looking cut off. It is now a semantic line (`divider:true`): the browser renders it as an `<hr>` that fits the page exactly, and the iMin bridge gets a `PAPER_COLS`-wide, centred dash run (the bridge takes text lines only, so dashes are still the best it can do — a true full-width rule needs a native `drawLine()` in the app). `flatten()` strips the `divider` flag before the payload leaves, since the bridge parses `PrintPayload.lines` strictly.
- **Shift submission bug** (`api.py`): `pos_open_shift` was calling `opening.insert()` without `opening.submit()`, leaving POS Opening Entries in Draft (docstatus=0). Added `opening.submit()` and changed `pos_close_shift` filter from `{"status": "Open"}` to `{"docstatus": 1}`.
- **kctBtn duplication** (`kitchen.html`): Repeated script runs produced duplicate `const kotBtn` declarations and duplicated button in card footer. Deduplicated.
- **Print button load failure** (all www pages): Closing tag pattern `</script></body></html>` (no newlines) was corrected to match actual file formatting with newlines.

### Changed
- **`api.py` is a package** — 7,338 lines split into `luuvcrm/api/`, 22 modules, one per domain (POS, orders, payments, kitchen, loyalty, customers, purchases, expenses, approvals, promos, guides, wastage, WhatsApp, printing, reporting…). `__init__.py` re-exports all 261 names, so every `luuvcrm.api.<name>` path stays exactly as it was — 144 whitelisted endpoints, `hooks.py`, the pages, and links already sent. Sending a WhatsApp message goes through one `wa._send_wa_reply` seam instead of four separate bindings.
- **The customer routes** — `/customer`, `/myorders` and `/my_orders` all 301 to `/cus`, as they already did; what changed is that the two stale 530- and 311-line copies of the retired order-history page behind them are gone (they never rendered — the redirect fires first), and all three now share one `redirect_to_cus()` rather than three copies of the query-string handling. The WhatsApp auto-reply links `/cus` directly instead of bouncing customers through `/myorders`.
- **One POS page** — `/pos2` and `/pos3` are deleted and `/pos` serves what used to be pos3, which is where the tablet layer, the iMin printer bridge and the Google-Docs print layouts actually live. The staging print-only guard went with them, and with it a redeclared `guestCheckClick` that shadowed the real one: the guest check autosaves the ticket again instead of answering "Send to kitchen first". `/admin`'s POS tile, `KNOWN_APPS`, the 401/403 redirect and the `get_print_templates` dotted path all follow. **Counter tablets bookmarked on `/pos2` need re-pointing.**
- `pos.html`, `waiter.html`, `kitchen.html`, `api.py` — all four files updated for print capability.
- `pos.html` — `LFTemplate` divider handling (`toLine`, `toHTML`, `flatten`).
